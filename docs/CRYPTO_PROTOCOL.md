# SFT1 — End-to-end encryption protocol

Implemented in `shared/src/wire-format.ts` and `shared/src/crypto/`. Runs
identically in the browser and in Node (both expose `globalThis.crypto`), which
is why the round-trip tests in `shared/src/crypto/*.test.ts` exercise the exact
code the browser runs.

Versioned so a future `SFT2` can coexist; every AAD and the manifest itself
carry the literal `"SFT1"` label.

## Keys

| Key            | Size    | Generated by                               | Lifetime                                                            |
| -------------- | ------- | ------------------------------------------ | ------------------------------------------------------------------- |
| File key (FEK) | 256-bit | sender's browser, `crypto.getRandomValues` | one transfer, never leaves the browser unwrapped                    |
| Link secret    | 256-bit | sender's browser                           | lives only in the URL fragment (`#k=...`), never sent to the server |
| KEK            | 256-bit | derived, never transmitted                 | derived fresh whenever a party needs to unwrap the FEK              |

The server never possesses a value the FEK can be derived from. Its entire view
of a transfer is opaque ciphertext, sizes, and counters.

## Key derivation

```
ikm  = linkSecret                                          (link-only)
ikm  = linkSecret ‖ PBKDF2-HMAC-SHA256(password,
         salt = "SFT1 pbkdf2 salt|" + transferId,
         iterations = 600 000, 256 bits)                    (link + password)

KEK  = HKDF-SHA256(ikm, salt = transferId, info = "SFT1 kek", 256 bits)
```

`deriveKek(linkSecret, transferId, password?)` in `shared/src/crypto/keys.ts`
implements this. Two different HKDF-derived values never share an `info`
label with a PBKDF2 salt or with each other — every derivation is bound to
`transferId`, so a KEK computed for one transfer is useless against another.

## Wrapping the file key

```
wrapNonce   = random 12 bytes
wrappedKey  = AES-256-GCM(KEK, wrapNonce, aad = "SFT1|wrap|" + transferId, FEK)
```

`wrapFileKey` / `unwrapFileKey` in `keys.ts`. The wrap nonce is independent of
the chunk nonce scheme below — it is used exactly once per transfer, so a fresh
random nonce is simpler than a counter and equally safe.

## Chunking

Plaintext is split into `chunkSize` pieces (default `CHUNK_SIZE_BYTES`, 4 MiB;
configurable per transfer). `chunkCount = ceil(size / chunkSize)`, computed
identically by both sides — a 0-byte file has `chunkCount = 0`.

```
noncePrefix   = random 8 bytes, once per transfer
chunkNonce(i) = noncePrefix ‖ u32be(i)
chunkAad(i)   = "SFT1|chunk|" ‖ transferId ‖ "|" ‖ u32be(i) ‖ "|" ‖ u32be(chunkCount)
ciphertext[i] = AES-256-GCM(FEK, chunkNonce(i), chunkAad(i), plaintext[i])
```

A random-but-unique-per-transfer key plus an 8-byte random prefix plus a 4-byte
counter gives a nonce that never repeats for the life of the FEK, which is used
for exactly one file.

Binding **both** the chunk's own index and the total chunk count into its AAD
is what makes the chunk _sequence_ authenticated, not just each chunk's bytes:

- **Reordered or duplicated chunks** fail because a chunk's AAD is tied to the
  slot it was encrypted for — decrypting ciphertext from slot 2 as if it were
  slot 3 fails the GCM tag check.
- **Truncation** (a dropped final chunk) fails because the decryptor is told
  `chunkCount` out-of-band (the server-reported count) and requires a
  ciphertext blob for every index up to that count; a short delivery throws
  before any decryption is attempted.
- **A lied-about `chunkCount`** (server claims fewer chunks than it truly
  stored) fails because the manifest itself was encrypted with the _true_
  count baked into its own AAD — see below.

## The manifest

Filename, MIME type, plaintext size, and chunk size are secret from the
server, so they travel as an encrypted JSON manifest rather than columns:

```
manifestNonce = noncePrefix ‖ 0xFFFFFFFF        (an index no real chunk uses)
manifestAad   = "SFT1|manifest|" ‖ transferId ‖ "|" ‖ u32be(chunkCount)
manifest      = { v: 1, name, type, size, chunkSize }
encrypted     = AES-256-GCM(FEK, manifestNonce, manifestAad, JSON(manifest))
```

`decryptFile` decrypts the manifest **first**, using the caller-supplied
`chunkCount`. Because that AAD only authenticates under the count truly used
at encryption time, a successful decrypt proves the supplied count is genuine.
`decryptFile` then re-derives `ceil(manifest.size / manifest.chunkSize)` and
requires it to equal the supplied count — a redundant, defense-in-depth check,
since a genuine manifest can never disagree with the count that unlocked it.

The decrypted manifest is parsed with `manifestSchema` (`shared/src/manifest-schema.ts`)
before anything trusts its shape — authenticated does not mean shaped, so it
still crosses a validation boundary like any other network-adjacent data.

## What this buys, and what it doesn't

The server can be fully malicious — swap bytes, replay old chunks, lie about
counts, serve a different manifest — and every case above is either rejected
outright or caught by the client. What it cannot do: the browser tab itself is
trusted, so a compromised endpoint (malicious extension, backdoored OS) still
sees plaintext; that is out of scope for any protocol running there. See
`plan.md` §2 for the full threat model.

## Password-gated links

`deriveKek`'s password branch changes the PBKDF2 output, which changes the
HKDF `ikm`, which produces a different KEK — a wrong password fails to unwrap
the FEK through the same fail-closed mechanism as a wrong link secret. The
round-trip tests currently only exercise the link-only path directly on the
FEK; a dedicated test for the password/link-secret KDF branch is still to be
written.

The server-side verifier is a **separate** derivation from the same PBKDF2
output, under a different HKDF `info` label (`"SFT1 server verifier"` vs
`"SFT1 kek"`), computed by `derivePasswordVerifier` in
`shared/src/crypto/keys.ts`. This is deliberate: the value the browser sends
to the server for rate-limited checking is cryptographically independent of
the value contributing to the KEK, so a server compromise that leaks the
stored verifier hash does not help decrypt any file — it authenticates
knowledge of the password without being the same secret the file's
confidentiality depends on. The server never sees the password itself, only
this verifier, Argon2id-hashed at rest (`transfers.gate_verifier_hash`).

Wired up in `server/src/routes/upload.ts` (finalize accepts `gate` and
`passwordVerifier`) and `server/src/routes/download.ts` (`POST /grant`
requires a matching verifier before a download slot is consumed — a wrong
password never burns the sender's download-count limit).
